# Fiscal XML architecture
- DPS issuance must use reserveValidatedDps before atomic number/row allocation: reject self-recipient, invalid approximate-tax/special-regime matrices and withholding without national recipient/address; omit zero discounts to avoid business rejections without consuming numbers.
- DPS tests fix only TSSerieDPS ^/$ literals in memory (official defect); ZIP stays intact. XML rejects DTD/entities and keeps decimal strings.
- Issuance uses an atomic durable key/snapshot/number/row RPC; ambiguous sends reconcile under database leases, never retransmit. Terminal transitions enqueue webhooks atomically; only API waitUntil triggers immediate delivery, otherwise the scheduler queue persists.
- New automatic series start at 900; explicit send-only E0014 allows five durable skips under leases with the same invoice/idempotency key, retaining each externally used number/XML/response to prevent reuse. Ambiguities never skip.
- API and panel share a server-only DANFSe renderer with embedded font/logo and authorized XML only, except current status and receipt preference, to prevent drift with live company records.
- NFS-e event requests (pedRegEvento) and the DPS subst group come from one builder module that enforces the official TSString/TSMotivo character set and E0812/E0042 issuer checks before any send, so invalid text never reaches the government.
- Cancellation/analysis requests persist an event row under a lease before sending; ambiguous replies are confirmed only by consulting the event (15-minute 404 rule) and E0840/E0802/E1805 refusals consult before refusing, so a fiscal event is never re-sent blindly. Invoice status, timeline and webhooks change atomically in the finish RPC.
- Substitutions reuse the issuance path with the subst group; the original turns substituted only inside the invoice finish RPC when the substitute is authorized, so a rejected substitute never alters the original.
- Every DPS/event text is normalized (fiscal-text) before validation and the stored text is exactly what is sent; refused characters fail with 422 before numbering.
- ADN sync runs only on panel requests (the Scheduler just continues open requests) and state is per CNPJ and environment (companies repeat across organizations): cursor leases, one row per NSU, one official document per key and one event per key/code/sequence; event application, timeline and webhook outbox live in SQL functions so re-processing is idempotent and final states never regress.
- External/received NFS-e visibility requires proof of possession (a company of that CNPJ with a certificate in the reader's organization) evaluated inline in RLS under the caller's own policies; notem-issued notes stay with the issuing organization.
- Government payloads are decoded tolerantly (plain, base64, gzip, base64 of base64-gzip) and read without DTD/entities; decoded `xml` fields take precedence over `arquivoXml`, and event sequences are sent as text (accepted by every transmissor version).
- Fiscal XML lives only as gzip files in the private `fiscal-xml` bucket (no storage policies; service role only), content-addressed with size/SHA-256 in `fiscal_xml_files`; servers upload and verify before the RPC, which stores only references atomically, so a note is never authorized nor an event registered without its file. The stored DPS is the number-1 base; Id/nDPS are applied from the row when sending.
- DPS layout profiles live only in dps-layout.ts and buildDps always receives the layout explicitly; the layout is re-decided right before each send (sandbox always the newest, production by the admin-only, audited platform_settings date) and a stored base in another layout is converted with the same number under the dispatch lease, so no DPS reaches the government in a layout the government no longer accepts.
- Readers of NFS-e/DPS fields that moved between layouts go through nfse-layout-read.ts, so DANFSe, ADN and events accept both formats.
- CNPJ values pass only through normalizeCnpj/isValidCnpj (TS) and normalize_cnpj/is_valid_cnpj (SQL), and access keys/Ids only through the fiscal-ids.ts structure (CNPJ at key positions 10–23), never digit-only patterns, so alphanumeric CNPJ works in every path; layouts without alphanumeric support refuse it before numbering and conversion to them fails as "not sent".
